# Agents know co

> **Preview, coming next.** This is in review in
> [openonion/connectonion#2355](https://github.com/openonion/connectonion/pull/2355)
> and not in any ConnectOnion release yet. `co skills index` does not exist in
> the current stable or preview package.

## Why it exists

A skill is loaded only when the agent already suspects it needs one. Before
this change, nothing told Codex or Claude Code that `co` exists at all. Ask
Codex "what's open on my Linear board?" and it went looking for a `linear`
binary, searched for environment variables, and ended with "connect Linear".

So global `co init` now writes a short, generated command index into the file
each coding agent reads at the start of every session:

| Tool | File | Written when |
|------|------|--------------|
| Codex | `~/.codex/AGENTS.md` | `~/.codex` exists |
| Claude Code | `~/.claude/CLAUDE.md` | `~/.claude` exists |

With the index in place, the agent runs `co commands`, opens
`co linear --help`, and answers from `co linear issues`.

### What it changed in a real A/B

Six `codex exec` runs (codex-cli 0.162.1) asked "What's open on my Linear
board?" from an empty directory, each with a throwaway `CODEX_HOME`. The only
difference between the two arms was the index in `$CODEX_HOME/AGENTS.md`.

| Arm | Used `co linear` | Answered |
|---|---|---|
| Without the index | **0 of 3** | none: each asked the user to "connect Linear" |
| With the index | **3 of 3** | all three: `co commands` → `co linear --help` → `co linear issues --json`, 4 open issues |

Codex only. Claude Code reading the block was not measured.

## What gets written

The block sits between two markers that carry the installed version. Nothing
outside the markers is ever changed:

```markdown
<!-- co:begin 1.9.2 -->
## ConnectOnion (`co`) — generated by `co init`; refresh: `co skills index`; remove: `co skills index --remove`
- You have `co`, the ConnectOnion CLI. Below is every top-level command.
- For outside services (mail, chat, calendars, issue trackers, files), handing work to someone or another machine, or memory: run `co commands` and read `co <cmd> --help` before using a browser or writing a script.
- Don't look for credentials yourself: run the command; if a key is missing, it says how to add it.

co linear — Linear issues from the terminal, with your personal API key: list, read, search, create, update, comment.
...
<!-- co:end -->
```

It is generated from the CLI itself: one line per visible top-level command,
hidden and deprecated commands left out, experimental and preview ones labelled. It cannot
drift from what `co` really has. Subcommands stay in `co <cmd> --help`. About
56 lines and about 1,100 tokens.

## How it stays current

All through the same function:

- **`co init`** (global) writes it, after running `co skills link`, and prints
  each path it changed and how to remove the block.
- **Agent start** (`host()`, so `co ai` too) refreshes a block whose version
  stamp differs from the installed version, printing one line per file it
  changed. When the block is current it only reads the stamp, about 1 ms.
- **`co doctor`** reports a missing or stale block under
  **Skills → Command index**, with `Next: co skills index`.

A machine with neither `~/.codex` nor `~/.claude` (a `co deploy --to` server,
Docker, CI) is never touched. A missing tool directory is never created.

Project `co init ./` does not write the block; only global `co init` does.
`CODEX_HOME` and `CLAUDE_CONFIG_DIR` are not honoured: the block always goes to
`~/.codex` and `~/.claude`.

## Refresh or remove it

```bash
co skills index            # write or refresh the block
co skills index --remove   # take it out again
```

`--remove` takes out only the block. If the command created the file and the
file holds nothing else, the file is deleted.

Edits you make **inside** the markers are lost at the next refresh; the block's
header says it is generated. Put your own notes outside the markers.
